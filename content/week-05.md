The brief is where research becomes a mandate. If someone read only this document, they should understand what's broken, what it costs the business, and exactly what you're going to build.

## Due this week

### Feature scope draft

- Problem statement, user and business
- Design opportunity
- Value proposition, one sentence
- Feature scope for homepage and PDP
- Key discovery questions and success metrics

## Session plan

01. **Writing a problem statement twice** — Once from the user's side, once from the business's. Both have to be true at the same time.
02. **Design opportunity & value proposition** — The framework: for [audience] who [need], this redesign [does what] unlike [current state].
03. **Feature scope** — Homepage and PDP, feature by feature. Must-have / should-have / out-of-scope, each with a one-line reason.
04. **Success metrics** — What would tell you this redesign worked? Behavioral and qualitative, not vibes.
05. **Peer review** — Swap briefs. Mark every sentence that states an opinion as a finding.

## In-class activity: The brief, in one sitting

1. Problem statement, user perspective — anchored to a specific audit finding.
2. Problem statement, business perspective — what the friction plausibly costs.
3. Value proposition using the framework, in one sentence.
4. Feature scope table for both pages, with must / should / out and reasons.
5. Five key discovery questions still open, and the success metrics you'd track.

## Working with AI this week

- “Here's my problem statement and feature scope. Which features don't actually address the stated problem?”
- “What would a skeptical stakeholder ask about this value proposition?”
- Every feature in scope must trace back to a documented audit finding or research theme. Cut anything that can't.

## Evidence to log

**Critical Curation**. AI's scope critique and which cuts you accepted or rejected, with reasons
**Reflective Reasoning**. Why these features and not the obvious extras
